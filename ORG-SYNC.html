Citizen's Edge Companion

Org sync reference

How a Companion talks to its org’s Hub (Citizens.Edge.Org), seen from the Companion: setup, what is queued and sent, and where the replies are stored. The Hub’s side (routes, sign-in, consent checks) is Citizens.Edge.Org/docs/API.md. Each field and who can see it: Citizens.Edge.Org/docs/DATA-INVENTORY.md. The code is the ce-sync crate; its tables are in docs/DATABASE.md.

Nothing leaves the machine until sync is set up (sync setup), and then only what the sharing switches and the member’s consent on the Hub allow.

A UI never talks to the Hub. The Companion pulls the data, decides what counts and sends the result to the UIs.

Setup and credentials

sync setup --url <worker> --key <key|-> first calls GET /me with the key. Only if that works is the key stored and the URL saved in sync_settings. The key goes into the system keyring (Linux: Secret Service via secret-tool; Windows: Credential Manager). It is passed to the keyring tool on stdin, never on a command line, and never appears in a log or an error. The key is a member key, or a device key from the Hub’s sign-in (/auth/device/*).

Setting up against a different URL than before replaces the org: the pulled org data is dropped, and anything still pending in the outbox is marked rejected (“sync URL changed before it was sent”) rather than sent to the new org.

What is shared

sync share and sync.share set sync_settings:

SwitchValues (default)Sends
sightingsoff, confirmed (default), autosighting events: a handle read in chat or as a target, with place, shard and the Companion’s confidence. confirmed queues one only after the user confirms it (sightings.confirm); auto queues each read. Party-panel reads are never shared
stockon/off (off)stock events: one per capture and terminal tab, all rows
presenceon/off (on)your shard and ship, never location (POST /presence)
blueprintson/off (off)a blueprints event: the ids of the blueprints you have, as the Companion decides them. A full snapshot, queued only when the list changed; turning it on sends the current list afresh

Also sent, on purpose: an officer’s org tag (tag event, from org.tag or tag --org-tag) and your own stance on a player or org (stance). Never mapped: party members, mission participants, deaths, trades, location history, chat text. Screenshots stay local: an event carries only the local capture id, so an officer can ask for the evidence. Imported screenshots are never shared.

The Hub applies its own gate on top: the member must have accepted the current consent text, and sighting, stock, stance, blueprints and fight need their own consent switch. A refused event comes back in rejected with a reason.

Catch-up: sync catch-up [--since <date>] [--dry-run] queues what the settings allow from captures taken before sync was set up or while sharing was off. Safe to repeat: ids already queued are kept.

The sync loop

sequenceDiagram
  participant U as User / UI
  participant C as Companion
  participant S as companion.db
  participant H as Hub
  U->>C: confirm a sighting, set a tag, a capture finishes
  C->>S: sync_outbox (status pending, a fresh UUID)
  loop every 60 s, and on sync.now
    C->>H: GET /me
    H-->>C: role, epoch, lockdown
    C->>S: sync_state (role, lockdown, epoch)
    C->>H: POST /events (up to 1000 pending, 200 per call)
    H-->>C: accepted, duplicates, rejected, epoch
    C->>S: outbox sent or rejected
    C->>H: GET /events?after=cursor (pages of 500)
    C->>S: org_events, cursor
    C->>H: GET /ratings?after=cursor
    C->>S: org_ratings, ratings cursor
    C->>S: derive org state, update contacts and org tags
  end
  C-->>U: sync.status, contacts, alerts when a tag changed
  • The outbox (sync_outbox) is the only way out. An entry is pending until the Hub answers; then sent (accepted or duplicate) or rejected (with the reason). An undelivered entry stays pending and is re-sent with the same id, so a retry cannot double-count: the Hub dedupes per member on the event id.
  • Failures: network errors, 5xx and 429 retry with exponential backoff (the Hub’s Retry-After wins when longer, capped at a minute). 401 means the key is revoked or expired: the Companion sets needsSetup and stops until sync setup runs again. 423 is a lockdown: the outbox stays pending. Any other status fails that run at once, and sync.status shows it in error.
  • Epoch: every Hub answer carries an epoch. When it changes (the Hub’s database was restored), the Companion drops its pulled org data and pulls again from 0. It never re-pushes what it already sent.
  • Cursors: sync_state.cursor for events and ratings_cursor for ratings; a pull that does not advance its cursor is an error, not a loop.
  • Derived state: org tags, standings and the org’s recent sightings are computed from the stored org_events and org_ratings, never kept as a second copy. The user’s own value and the org’s are stored apart and the user’s wins (docs/UI-LOGIC-AUDIT.md).
