Companion protocol reference

The WebSocket and HTTP API the Companion daemon offers to the /live page, the overlay and the TUI. The machine-readable spec is crates/ce-protocol/protocol.schema.json (current version in its protocolVersion: 1.42.0; 55 client messages, 43 server messages). This page is the readable index of it: what connects, what each scope may do, and every message with its fields. When a message changes, change the schema, src/validate.rs and this page in the same PR (a test fails if a message type or the version is missing here).

Rules that shape the API (CLAUDE.md): the UIs talk only to the Companion; the Companion decides and the UIs show (decided values come with *From flags); changes are additive and bump the protocol semver (protocol-semver --base <ref> in CI). The Hub is a different API: Citizens.Edge.Org/docs/API.md; how the Companion uses it is docs/ORG-SYNC.md, and the commands that share this handler layer are docs/CLI.md.

Connecting

  • Address: ws://127.0.0.1:47823 by default (--port, --host). The daemon binds 127.0.0.1.
  • Token: the pairing token in the data dir (token, 0600). Offer it as the WebSocket subprotocol ce.token.<token> (a browser cannot set headers), as Authorization: Bearer <token>, or, for older pages, as ?token=. The subprotocol form keeps it out of URLs, history and logs.
  • Origin: a request with no Origin header is a native client started by the user on this PC (overlay, TUI, CLI tools). A browser page must match the allowlist exactly: https://citizensedge.space, https://staging.citizensedge.space, https://citizens-edge.pages.dev, https://citizens-edge-staging.pages.dev, http://localhost:3000, http://127.0.0.1:3000. There is no wildcard: a preview deploy or another site works only if the user starts the daemon with --allow-origin.
  • Host: the Host header must name localhost or an IP address. A page reaching the daemon under another domain name (DNS rebinding) gets 403.
  • Limits: a WebSocket message or frame may be up to 1 MiB, an HTTP body up to 4 MiB (413 above that), and an HTTP request has 30 seconds. Responses carry x-content-type-options: nosniff and referrer-policy: no-referrer.
  • First message: the server sends hello (protocol version, status) then a snapshot that already holds everything on disk. Every outgoing message is validated against the schema; a breach is logged once per type and problem per five minutes.
  • Pairing a reply to a request: a request may carry requestId; the reply echoes it. Messages without one are matched by type.

Scopes

Every client message needs one scope (crates/ce-core/src/scope.rs); a message above the connection’s scope is refused.

ScopeAllowsHeld by
viewreads and subscriptions; change nothingany connection
controlthe user’s own choices that stay on this PC: tags, notes, pins, local settings, blueprints, truth review, suggestionsa browser page
adminanything that opens egress (org sharing, RSI lookups), destroys data (delete, merge, cleanup, reprocess) or changes what the org sees (an officer tag)a native client (no Origin); a browser page only after elevation

Elevation: a page sends auth.elevate, the Companion shows a six-digit code, and the user approves it on this PC with ce-companion approve <code>. That grants that one connection admin for ten minutes; the request is valid for two. A script injected into an allowed site therefore cannot turn sharing on or delete a contact silently.

Control socket

The CLI and TUI use a local Unix socket (Windows: a named pipe) protected by filesystem permissions, and send the command tree in crates/ce-cli/commands.json (the reference is docs/CLI.md). It is not part of this protocol, but the handlers are shared, so a command and its message do the same thing.

Examples

Worked examples with realistic values and what each field holds (docs/examples/protocol-examples.json; each is validated against the schema by a test). The full machine-readable contract, with these examples attached to their messages, is docs/generated/asyncapi.json (AsyncAPI 3.0).

subscribe: Start the live feed after the last event you have

since is the seq of the last event you received (the cursor of the snapshot on first connect). Omit it to get only new events.

  "since": 18342

Families

  • Capture and truth: capture, captures.* (list, update, reprocess), truth.* (queue, confirmed, confirm, stats, report, resolve; truth.changed and truth.invalidated are pushed). Reprocessing deletes that capture’s confirmations (admin).
  • Contacts: contacts.* and contact.*. Lists, filters, chip counts and views are decided here; a page renders them.
  • Orgs and suggestions: orgs.*, org.tag (an officer tag that is then shared; admin), suggestions.* (suggestions.groups returns the grouped, ordered, counted inbox).
  • Blueprints: blueprints.get (what the user has, with ownedFrom), blueprints.set (the user’s own switch), blueprints.known (the game’s published list with who has each and the missions that unlock them; a paged read).
  • Sync: sync.status, sync.now, sync.share (admin: org sharing switches).
  • State pushes: event, contacts, contacts.now, contact.alert, alert.speak, background.state, presence, system.cpu, sync.status.

Companion command-line reference

ce-companion <command> [options]. The WebSocket API is docs/PROTOCOL.md. Org sync, which the sync command drives, is docs/ORG-SYNC.md. The summary, options and command text below are generated from crates/ce-cli/commands.json, the same file --help and the shell completions read.Change the JSON, then this page.

How a command runs

  • Exit codes: 0 ok, 1 command error, 2 usage error.
  • With the Companion running (ce-companion start or daemon), commands run inside it over the local control socket (Unix socket; Windows named pipe, protected by filesystem permissions), on its own low-priority queues, through the same handlers as the matching WebSocket message. A command and its message do the same thing.
  • Without it, commands open companion.db directly. The offline reads (status, captures, logs, ocr-report, models, contacts aliases, truth stats|queue|history) open it read-only.
  • One Companion per data folder: start, daemon, demo and client are standalone; a second start finds companion.lock (an exclusive file lock holding the pid) or a listening socket and exits.
  • Heavy work waits for the game. Commands marked heavy (OCR re-reads, cleanup, maintenance) are held while Star Citizen runs; --now or --force overrides where the usage text says so.
  • --json prints a machine-readable result on commands marked --json.
  • Confirmation: commands marked confirms ask first on a terminal; --yes skips the question and is required without one; --dry-run shows the plan and changes nothing.
  • Output is plain text without colour or spinners unless stdout is a terminal.

Environment: CE_ENV (selects the environment), CE_SC_CHANNEL (the Star Citizen channel), CE_UPDATE_URL and CE_UPDATE_CHANNEL (the release feed), CE_REPORT_REPO (where crash reports are filed).

Companion database

The Companion keeps everything in one SQLite file, companion.db, in its data folder (Linux ~/.local/share/citizens-edge-companion/, Windows %LOCALAPPDATA%\CitizensEdgeCompanion). Only the running Companion writes to it (the ce-store crate). status, captures, logs, ocr-report, models, contacts aliases and truth stats|queue|history can read it with the Companion stopped. The Hub has its own database: Citizens.Edge.Org/docs/DATABASE.md. How the two connect: docs/DB-API-REPORT.md.

This is schema version 4, with 32 tables and 42 indexes. The schema as SQLite stores it is docs/generated/companion-schema.sql, made by cargo run -p ce-core --bin docgen; CI fails if it is out of date. A test fails if a table or column is missing from this page, so change this page in the same PR as a table. Findings and measurements are in DB-API-AUDIT.md and DB-API-REPORT.md.

Versioning

The version is stored in SQLite’s user_version (crates/ce-store/src/schema_version.rs).

  • Version 1 is the original set of tables, created when the store opens. A file with no version is brought to version 1.
  • Later versions are entries in MIGRATIONS. They are only ever added, applied in order, each in a transaction that also records the version. Never change one that has shipped.
  • A newer file is refused. An older Companion will not open a store written by a newer one.
  • Version 2: contact_seen (a copy of four contact_events columns) was merged into contact_events and dropped.
  • Version 3: CHECK constraints on three columns with a fixed set of values: sync_outbox.status, contact_suggestions.status and contact_links.link_kind. Each table is rebuilt with its rows and indexes. A value outside the set is changed to rejected, stale or alt first, so no row is lost. Tested on a copy of a real store: every row count was the same afterwards.
  • Version 4: HTML entities in names read from RSI (W&ouml;lfe, DraXon&trade;, Alor&amp;amp;rsquo;ad) are decoded in org_memberships, orgs, citizen_profiles, citizen_profile_lookups and rsi_cache. The decoder now knows every named entity and decodes names RSI escaped twice.
  • The store can be rebuilt: events comes from raw_lines, and the contact tables from events, contact_events and captures.

How the tables relate

The store has no foreign keys. Tables join by value and the Companion keeps them consistent. A foreign key would be wrong or unsafe in each case: contacts appear in sightings, profiles and org data before (or without) a contacts row; commodity_truth rows outlive an expired capture; a truth report outlives the truth row it was raised on; deleted_contacts, handle_aliases and storage_registrations keep their key after the thing is gone; and org_memberships is written for orgs the Companion has no orgs row for. A contact is identified by handle_key (the handle in lower case), a capture by id and an org by sid.

Your value and the org’s value for the same thing are stored separately (orgs.stance and contacts.personal_tag, against org_ratings). Yours wins, and the Companion decides which one is shown (docs/UI-LOGIC-AUDIT.md).

What stays on the machine

  • Everything above stays here until you delete it. raw_lines is never trimmed. Screenshots are tiered by storage.
  • Other players’ chat text is not stored (since protocol 1.42.0). A one-time job (chat-text-scrubbed) removed it from older captures.
  • contact_events records where a named player was seen: shard, location, and where you were. It is only sent to the org as opt-in sightings.
  • contact.delete removes the contact’s rows from contact_events and the other contact tables, and stops the name being added again. The handle still appears in events payloads, in the handles of captures.meta and in raw_lines (open item C2 in docs/DB-API-REPORT.md).
  • Data leaves the machine only through the opt-in paths in section 2 of docs/DB-API-AUDIT.md: org sync (the outbox), RSI lookups, the update check, reference data, the voice pack and hangar sync.

Not in this database

  • Reference data (ships, places, models, the game’s blueprints and missions) is built into the program from crates/ce-core/data/reference.json, made by fetch-reference-data from the Citizens.Edge.Data views. It is read-only.
  • Files: captures/, token, ocr-settings.json, logs/.
  • The pairing token is also kept in the browser’s localStorage.

Setup and credentials

sync setup --url <worker> --key <key|-> first calls GET /me with the key. Only if that works is the key stored and the URL saved in sync_settings. The key goes into the system keyring (Linux: Secret Service via secret-tool; Windows: Credential Manager). It is passed to the keyring tool on stdin, never on a command line, and never appears in a log or an error. The key is a member key, or a device key from the Hub’s sign-in (/auth/device/*).

Setting up against a different URL than before replaces the org: the pulled org data is dropped, and anything still pending in the outbox is marked rejected (“sync URL changed before it was sent”) rather than sent to the new org.

The sync loop

sequenceDiagram
  participant U as User / UI
  participant C as Companion
  participant S as companion.db
  participant H as Hub
  U->>C: confirm a sighting, set a tag, a capture finishes
  C->>S: sync_outbox (status pending, a fresh UUID)
  loop every 60 s, and on sync.now
    C->>H: GET /me
    H-->>C: role, epoch, lockdown
    C->>S: sync_state (role, lockdown, epoch)
    C->>H: POST /events (up to 1000 pending, 200 per call)
    H-->>C: accepted, duplicates, rejected, epoch
    C->>S: outbox sent or rejected
    C->>H: GET /events?after=cursor (pages of 500)
    C->>S: org_events, cursor
    C->>H: GET /ratings?after=cursor
    C->>S: org_ratings, ratings cursor
    C->>S: derive org state, update contacts and org tags
  end
  C-->>U: sync.status, contacts, alerts when a tag changed
  • The outbox (sync_outbox) is the only way out. An entry is pending until the Hub answers; then sent (accepted or duplicate) or rejected (with the reason). An undelivered entry stays pending and is re-sent with the same id, so a retry cannot double-count: the Hub dedupes per member on the event id.
  • Failures: network errors, 5xx and 429 retry with exponential backoff (the Hub’s Retry-After wins when longer, capped at a minute). 401 means the key is revoked or expired: the Companion sets needsSetup and stops until sync setup runs again. 423 is a lockdown: the outbox stays pending. Any other status fails that run at once, and sync.status shows it in error.
  • Epoch: every Hub answer carries an epoch. When it changes (the Hub’s database was restored), the Companion drops its pulled org data and pulls again from 0. It never re-pushes what it already sent.
  • Cursors: sync_state.cursor for events and ratings_cursor for ratings; a pull that does not advance its cursor is an error, not a loop.
  • Derived state: org tags, standings and the org’s recent sightings are computed from the stored org_events and org_ratings, never kept as a second copy. The user’s own value and the org’s are stored apart and the user’s wins (docs/UI-LOGIC-AUDIT.md).

The Rust core daemon (ce-companion __daemon)

ce-companion start --sc-dir <Star Citizen LIVE> [--data-dir D] [--port 47823] [--host 127.0.0.1] [--allow-origin O] [--web-url U] [--data-url U] [--ocr-model small|medium] [--ocr-threads N] [--no-hotkey] [--no-lookups]

The whole Companion core in one process: it tails Game.log into the SQLite store and the live state, serves the live protocol over WebSocket, takes and reads screenshots, answers the control socket for the Rust CLI and TUI, and runs contacts, org sync, RSI lookups, commodity truth review, combat, notifications and the CPU card. It uses the same companion.db, token file and port as the Node core, so run one or the other on a data dir: a live control socket for the data dir stops a second core starting.

Flags for tests and cautious runs: --no-hotkey skips the desktop portal binding (the first bind shows a dialog), --no-lookups never starts the RSI queue. Environment: CE_CREDENTIAL_STORE=file keeps the org sync key out of the OS keyring, CE_NOTIFY=off plays no sound and shows no pop-up, CE_FILE_LOG=off, CE_LOG_MAX_MB, CE_LOG_FILES as in the Node core.

What it does

Start-up: open the store, ingest log backups not seen yet, restore the live state from its snapshot plus newer events, resume the tailer from its checkpoint, catch up to the end of Game.log, then start the capture worker, the contacts runtime and the control socket, bind and print the /live link. A client that connects gets a snapshot that already holds everything on disk.

Live protocol: token and Origin checks, hello, snapshot, live event, subscribe replay, query; the capture messages (capture, captures.list, captures.update, captures.reprocess); contacts (contacts.now|counts|pin|category|trust|history|list|search|tag, contact.lookupProfile|correctHandle|merge|delete), orgs (orgs.list|refresh|lookup|trust, org.tag), suggestions.*, intel.settings, presence.list, sync.status|now|share, sightings.confirm, combat.timeline|settings, truth.queue|confirmed|confirm|stats|report|resolve. Pushes: contacts, contacts.now, contact.alert, alert.speak (an alert worth saying aloud, in parts, for the UI to speak: the daemon no longer speaks), background.state (whether the player is engaged and the Companion is holding its background reads, why, until when and how many are waiting: sent when it changes and on connect; a UI shows it so a hold is never silent), contact.deleted, contacts.counts, presence, suggestions, sync.status, truth.changed, system.cpu. Every outgoing message is validated against the exported protocol schema; a breach is logged once per type and problem per five minutes.

HTTP: /captures/:id/image|bundle|ocr|annotations (GET, PUT for annotations) and /captures/:id/rows/:n/crop (the raw row cut; the upright rectified cut needs OpenCV and the Node route falls back to the raw cut too), with the WebSocket’s token and Origin rules.

Capture path: the portal hotkey, the capture request and ce-companion capture [import <file>] queue a screenshot. One worker thread grabs through the gated KWin provider (no desktop fallback; an optional local ONNX privacy classifier vetoes the capture, and a configured one that cannot load refuses it), writes the processing sidecar, reads it, stores the events and pushes the result. A live HUD read leaves the canopy area and the colour passes to a background completion (the result is deferred), reads speculatively within two minutes of a HUD capture (a speculative read that turns out to be another screen retracts its contacts), and a kiosk gets a background read with every voter. Live captures run before background work and never preempt a running read. The OCR engine loads on first use and unloads after five idle minutes. It runs on the capture thread, which is lowered to nice 10 (I/O best-effort level 7) before the engine loads so that ONNX Runtime’s threads inherit it and the game keeps the CPU (ce-core/src/priority.rs; CE_OCR_NICE=<0-19> or off; Linux only).

Contacts, sync and RSI: a store connection per background job (WAL + a 5 s busy timeout), never the core’s lock held across the network. The org sync loop runs every 60 s; RSI lookups follow the Node queue’s rules (2 s spacing, 300 per hour, exponential backoff, forced lookups first). A hostile or KOS contact seen in the window raises one alert per level per session, pushed to clients and through the notification channels (audio and desktop; plans for Linux, macOS and Windows, run detached at nice 19). A stance change recomputes only the handles concerned and re-evaluates their recent target captures.

Build-time downloads (nothing is fetched while the Companion runs): ONNX Runtime is linked into the executable (ort download-binaries, cached in ~/.cache/ort.pyke.io). The PP-OCR V6 models are pinned by sha256 in models.lock.json; cargo build downloads the small model itself (ce-recognizer/build.rs; CE_OFFLINE=1 skips it); cargo run --release -p ce-core --bin fetch-models puts them in models/, the small model is then compiled into the executable (CE_REQUIRE_BUNDLED_MODELS=1 makes a missing file a build error), and the medium one is packaged in a models/ folder beside it (development falls back to ~/.cache/ppu-paddle-ocr; CE_OCR_MODELS_DIR overrides). The reference data (ce-core/data/reference.json) is committed. CI caches the cargo registry and target, the ONNX Runtime binaries and the models. models shows where each size comes from.

Control socket: status, capture, captures, contacts, tag, now, category, lookup, orgs, suggestions, sync, combat, notify, truth queue|confirm|unconfirm|report|reports|resolve|crop|stats, logs, backfill [--captures] [--geometry on|off], ocr-report [--quality [--truth <file>|confirmed] [--baseline <report>]], annotations export, models, truth export|import|check|corpus|history. The printed lines equal the Node CLI’s (commands-check.mjs compares them on a copy of the real database).

Diagnostics: <dataDir>/logs/companion.log (JSON lines, rotated by size), redaction of tokens and keys before anything is written, a panic hook that writes crash-<time>-<component>.json (message, source location, backtrace, a fingerprint and the last 20 log entries; the newest 10 kept), status.recentCrash.

Crash reports: every executable (ce-companion, its TUI, ce-overlay) installs the hook through the ce-crash crate; paths under the home folder are shown as ~. The next terminal run prints a one-line hint when a crash has not been looked at. ce-companion report shows the newest one and, only when you answer yes (or pass --open), opens a prefilled GitHub issue in the browser: --print shows the link instead, --list every record, --file <name> a particular one, --dismiss stops the hint, --repo owner/name (or CE_REPORT_REPO) files elsewhere. Issues go to the public releases repository (the Companion’s own is private). The program sends nothing and holds no token: you review the form and press Submit. The link is cut to fit a URL; the complete report is saved as logs/report-<fingerprint>.md to attach. The fingerprint (component, message without digits, source file) lets repeats be recognised. Native crashes (segfaults, GPU drivers) are not covered yet: that needs a minidump handler.

Geometry reader and the golden set

Kiosk captures are read by the geometry-first reader (ce-rectify, ce-pipeline/src/geometry.rs): the theme is classified, the panel localised (accent frame, observed edges, anchor snap), warped upright at 2x, re-straightened from its own lines, its dividers found, and the grid read cell by cell (else a checked text read of the same panel); the table lines go back through the normal parse. It is pure Rust: the OpenCV operations it needs are re-implemented after OpenCV’s own algorithms (ce-rectify/src/cv.rs). <dataDir>/ocr-settings.json {"ocr": {"geometryReader": true|false|"auto"}} is read for every capture (unset = on); captures.reprocess.geometry {id, geometry} and backfill --captures --geometry on|off override it for one run. The trace is commodity.geometry in the sidecar.

truth export|import|check|corpus|history work on the same tests/golden folder as the Node CLI (labels, baseline.json, history.jsonl and the corpus manifest are byte-compatible). The check reads the cases on the capture worker: the fast tier is the OCR over each crop, the full tier the whole pipeline (voters and geometry reader) over scratch copies of the originals. On the repo’s 78 golden cases the full tier scores 100% on every field, as the Node core does.

One executable, three modes

ce-companion is the only binary a user runs.

CommandWhat runs
start, or no argumentsThe Companion and, on a terminal, its live view, in one process. The Companion runs on its own thread; the view is a client of its control socket on the main thread; leaving the view stops the Companion. --no-ui, or stdin/stdout not a terminal, runs it headless with plain logs.
daemonThe Companion headless, for a service, systemd unit or autostart entry. --supervise (Linux) wraps it in the supervisor: ce-companion daemon is spawned as a child, restarted after a crash, SIGINT/SIGTERM forwarded, crashes logged to logs/supervisor.log.
client (alias tui)The live view of a Companion that is already running, over the control socket.

The view (ce-cli/src/tui.rs) is a console, not just a status display: status panes on tall terminals, a scrolling feed (the Companion’s log lines, finished captures and events, polled from the hidden feed --since <seq> control command), and a prompt. Typed commands go to the Companion over the control socket on their own thread and their output lands in the feed. Prompt: help [command], clear, quit; Tab completes commands, subcommands and flags; Up/Down is history (<data dir>/prompt-history.txt); PgUp/PgDn scroll the feed, Ctrl-End returns to live; Ctrl-C clears the line, then quits on an empty one. start, daemon, client and update run outside the view.

Every other command talks to the running Companion over the control socket; the read-only ones also run with none. One Companion per data dir (an flock on companion.lock; under --supervise the supervisor holds it for the child). --core <exe> / CE_CORE run another executable under --supervise (the tests do). A Windows updater swaps the one file after stopping the process.

With no Companion running

The read-only commands listed in CLAUDE.md run in the calling process (offline.rs): the store is opened as the daemon would open it, the command’s handler runs, the answer is printed as usual (status says the Companion is not running). Contact links (alts and renames)

contact_links (ce-store) holds one row per link between two contacts: handle_key, linked_key, link_kind (alt, same, renamed = handle_key was renamed to linked_key), link_source (manual/suggested), confidence, reasons, linked_at. Local only, never synced. Each handle stays its own contact (own RSI profile, orgs, sightings); a group is whatever you reach following links either way.

  • contacts link <handle> <handle> [--kind alt|same|renamed], contacts unlink <handle> <handle>, contacts aliases <handle> (the last also works with no Companion running).
  • Only warnings travel. A contact with no stance of its own takes the worst of wary/hostile/kos tagged on a linked handle (intel.stanceSource = linked, intel.linkedStance = {stance, via}); friendly/neutral/ally are never passed on, so a wrong link can make a contact look more dangerous, never safer. An own tag (or org tag) always wins. The same rule feeds the stance counts.
  • The contact view lists the group in intel.linked (protocol 1.15.0, additive); contacts lines show also:<handles>.
  • Deleting a contact removes its links; folding a misread into the real handle moves its links.

Stances and alerts: hostile, wary, KOS

kos and hostile are hostile: the friend-or-foe rank hostile, “turned hostile”, hostile-org suggestions and the combat target flag all key off is_hostile_stance (ce-contacts). wary is a lesser warning for a contact to watch (a PvP group such as ZAP, say), not a threat:

  • rank wary (sorts just below hostile on the “now” list and keeps the hostile window), alert level wary, notification kind wary-sighted (severity info, so a softer sound; spoken as “Wary, <handle>”). It is on by default and has its own switches: notify set wary on|off, notify set desktop-wary on|off, notify test --kind wary.
  • a wary alert fires once per level: a wary contact who later turns hostile alerts again as hostile.
  • a wary tag (or a wary org) still lowers trust, like a hostile one (is_warning_stance).
  • the org sync wire carries wary as a hostile status with a [WARY] note marker (unchanged), so older Workers keep working.

Who may do what (scopes)

Every WebSocket message needs one of three scopes (crates/ce-core/src/scope.rs lists them):

  • view: reads and subscriptions.
  • control: the user’s own choices that stay on this PC (tags, notes, pins, local settings, blueprints, truth review).
  • admin: anything that opens egress (sync.share, intel.settings, sync.now, org.tag), destroys data (contact.delete, contact.merge, storage.configure, storage.cleanup, captures.reprocess*, truth.resolve).

A native client (the overlay, the TUI: no Origin header) was started by the user on this PC and holds admin. A browser page holds control. A page that needs an admin action gets auth.required { for, scope }, sends auth.elevate, and receives auth.elevation { code, expiresInS }. The user approves on this PC with ce-companion approve [code] (the control socket, which only a process that can read the token reaches); the daemon then broadcasts auth.scope { connection, scope: "admin", expiresInS } and that connection keeps admin for ten minutes. Each connection is told its own id and scope right after hello (auth.scope).

A page offers the token as the WebSocket subprotocol ce.token.<token> (a browser cannot set headers on a WebSocket) instead of ?token= in the URL, where it ends up in history and logs. ?token= still works for older pages and will be removed once the web app has moved (protocol 1.42.0).
