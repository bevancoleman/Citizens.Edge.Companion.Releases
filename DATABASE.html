Citizen's Edge Companion

Companion database

The Companion keeps everything in one SQLite file, companion.db, in its data folder (Linux ~/.local/share/citizens-edge-companion/, Windows %LOCALAPPDATA%\CitizensEdgeCompanion). Only the running Companion writes to it (the ce-store crate). status, captures, logs, ocr-report, models, contacts aliases and truth stats|queue|history can read it with the Companion stopped. The Hub has its own database: Citizens.Edge.Org/docs/DATABASE.md. How the two connect: docs/DB-API-REPORT.md.

This is schema version 4, with 32 tables and 42 indexes. The schema as SQLite stores it is docs/generated/companion-schema.sql, made by cargo run -p ce-core --bin docgen; CI fails if it is out of date. A test fails if a table or column is missing from this page, so change this page in the same PR as a table. Findings and measurements are in DB-API-AUDIT.md and DB-API-REPORT.md.

Versioning

The version is stored in SQLite’s user_version (crates/ce-store/src/schema_version.rs).

  • Version 1 is the original set of tables, created when the store opens. A file with no version is brought to version 1.
  • Later versions are entries in MIGRATIONS. They are only ever added, applied in order, each in a transaction that also records the version. Never change one that has shipped.
  • A newer file is refused. An older Companion will not open a store written by a newer one.
  • Version 2: contact_seen (a copy of four contact_events columns) was merged into contact_events and dropped.
  • Version 3: CHECK constraints on three columns with a fixed set of values: sync_outbox.status, contact_suggestions.status and contact_links.link_kind. Each table is rebuilt with its rows and indexes. A value outside the set is changed to rejected, stale or alt first, so no row is lost. Tested on a copy of a real store: every row count was the same afterwards.
  • Version 4: HTML entities in names read from RSI (W&ouml;lfe, DraXon&trade;, Alor&amp;amp;rsquo;ad) are decoded in org_memberships, orgs, citizen_profiles, citizen_profile_lookups and rsi_cache. The decoder now knows every named entity and decodes names RSI escaped twice.
  • The store can be rebuilt: events comes from raw_lines, and the contact tables from events, contact_events and captures.

How the tables relate

The store has no foreign keys. Tables join by value and the Companion keeps them consistent. A foreign key would be wrong or unsafe in each case: contacts appear in sightings, profiles and org data before (or without) a contacts row; commodity_truth rows outlive an expired capture; a truth report outlives the truth row it was raised on; deleted_contacts, handle_aliases and storage_registrations keep their key after the thing is gone; and org_memberships is written for orgs the Companion has no orgs row for. A contact is identified by handle_key (the handle in lower case), a capture by id and an org by sid.

Tables

Types: text, integer, number, JSON (JSON stored as text). Times are ISO 8601 UTC text, e.g. 2026-10-26T07:40:43.938Z, unless the column says milliseconds. “optional” means the column can be empty. Examples are made-up or taken from real use.

The log

raw_lines

Raw lines from the Game.log files. Key: file, line_no.

ColumnTypeDescription
filetextLog file name, e.g. Game.log or Game Build(13220821) 25 Nov 26 (23 11 30).log
line_nointegerLine number in that file
texttextThe line as written in the log

events

Events parsed from the log lines, and from screenshots read by OCR. Key: seq.

ColumnTypeDescription
seqintegerRunning number in insertion order. Clients subscribe from it
idtextUnique event id, e.g. b7fd105117ef1a4b
kindtextEvent type, e.g. session.start, location.change, party.joined, ocr.sighting
attextWhen it happened, ISO 8601 UTC, e.g. 2026-10-26T07:40:43.938Z
payloadJSONThe event as JSON: its id, time, source (log or ocr, with the file or screenshot) and the fields for its kind, e.g. handle for a sighting

ingested_files

Log files that have been read, so a backup log is not read twice. Key: name.

ColumnTypeDescription
nametextLog file name
sizeintegerSize in bytes when it was read
mtime_msintegerFile modified time, unix milliseconds
ingested_attextWhen it was read, ISO 8601 UTC

checkpoints

Named positions and one-time job markers. Key: name.

ColumnTypeDescription
nametextWhat it marks, e.g. tail:Game.log (how far the log has been read), live-state, captures:folders, chat-text-scrubbed
valueJSONIts data as JSON, e.g. {"offset":1829479,"lineNo":8276}
updated_attextWhen it was last changed, ISO 8601 UTC

Who writes what

  • Log reader: raw_lines, events, ingested_files, checkpoints, and the contacts and org memberships found in log events.
  • Screenshot reader: captures, contact_events (names read from screenshots), commodity_truth.
  • Background work (lookups, upkeep, storage): contact_categories, contact_suggestions, citizen_profiles, citizen_profile_lookups, rsi_cache, maintenance_runs, storage_registrations.
  • Org sync: org_ratings, org_events, sync_state, sync_outbox, and orgs and org_memberships from the org feed.
  • You (web page, overlay, CLI, TUI): contacts, contact_categories (category, trust), contact_pins, contact_links, handle_aliases, deleted_contacts, blueprint_overrides, intel_settings, combat_settings, sync_settings, truth confirmations and reports, orgs (trust, stance), annotations and storage policy.

Your value and the org’s value for the same thing are stored separately (orgs.stance and contacts.personal_tag, against org_ratings). Yours wins, and the Companion decides which one is shown (docs/UI-LOGIC-AUDIT.md).

What stays on the machine

  • Everything above stays here until you delete it. raw_lines is never trimmed. Screenshots are tiered by storage.
  • Other players’ chat text is not stored (since protocol 1.42.0). A one-time job (chat-text-scrubbed) removed it from older captures.
  • contact_events records where a named player was seen: shard, location, and where you were. It is only sent to the org as opt-in sightings.
  • contact.delete removes the contact’s rows from contact_events and the other contact tables, and stops the name being added again. The handle still appears in events payloads, in the handles of captures.meta and in raw_lines (open item C2 in docs/DB-API-REPORT.md).
  • Data leaves the machine only through the opt-in paths in section 2 of docs/DB-API-AUDIT.md: org sync (the outbox), RSI lookups, the update check, reference data, the voice pack and hangar sync.

Not in this database

  • Reference data (ships, places, models, the game’s blueprints and missions) is built into the program from crates/ce-core/data/reference.json, made by fetch-reference-data from the Citizens.Edge.Data views. It is read-only.
  • Files: captures/, token, ocr-settings.json, logs/.
  • The pairing token is also kept in the browser’s localStorage.
